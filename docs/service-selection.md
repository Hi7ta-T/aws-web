## 各サービスの比較、選定理由
以下の順番で選定理由を説明。

- ロードバランサー
- サーバー
- DB
- VPC外リソース
- (補足)Webサーバー
- (補足)インスタンスタイプ

### ロードバランサー
| 名称 | 対象<br>プロトコル | プロトコル層 | 選定可否 
|:-----:|:-----:|:-----:|:-----:|
| ALB | HTTP/HTTPS | L7 | ◎ |
| NLB | TCP/UDP/TLS | L4 | ◯ |
| GWLB | ほぼ全て | L3,L4 | ✕ |

- 今回は口コミ数やその内容を管理するWebアプリケーションを作成するため、Web通信のHTTP/HTTPSリクエストの受け入れとなる。
- NLBはHTTP/HTTPSリクエストの通信は可能だが、プロトコル層がL4層のためポート番号単位での区別となり、パスの内容での詳細な振り分けは難しい。
- また、GWLBに関しては通信とセキュリティ製品を中継するサービスであり、セキュリティ性の強化で用いられることがあるため、今回の成果物には適さない。<br>

以上のことから、プロトコル層がL7層でパスやURLで振り分け先の指定が可能であるALBを採用した。


### サーバー
| 名称 | サーバー<br>有無 | 特徴 | 選定可否 
|:-----:|:-----:|:-----:|:-----:|
| EC2 | 有 | NW設計、通信制御等を自らで設定 | ◎ |
| Lambda | 無　<br> （サーバーレス）| サーバー管理不要<br>スケーリングはAWS側で実施 | △ 
| Lightsail | 有 | 構築が容易<br>詳細なVPC設計不可 | ◯ |

- 今回はサーバーの機能である通信制御やスケーリングについて実構築し、<br>
可用性を意識したサーバー構築ならびにNW設計を学習することが目的である。
- Lambdaはサーバーレスサービスのため、インフラ基盤が抽象化され、サブネット配置やルーティングなどのNW設計の詳細な理解が進みにくい。<br>
また、クライアント側でのスケーリングの設定が不要なことから今回の作成目的にはそぐわないと判断した。<br>
- LightSailはサーバーとしての実体は存在するが、構築が容易であるためEC2のように可用性を意識した自由なサーバーやNWの構築を行うことが難しい。<br>

以上のことから、Lightsailよりコストは高くなるものの、サーバーやNWの詳細な構築を行うことができるEC2を採用した。

### DB
| 名称 | 操作方式 | 特徴 | 選定可否 |
|:-----:|:-----:|:-----:|:-----:|
| RDS | SQL | 使用できるDBが豊富 <br> Multi-AZは設定必要 | ◎ |
| Aurora | SQL | 高性能でフェイルオーバーが早い <br> 最初からMulti-AZが適用 | ◯ |
| DynamoDB | NoSQL | データを自由な構造で格納可能 <br> 標準でMulti-AZ構成 | △ |

- 今回使用するデータは口コミの内容、年齢層や性別と集計する内容が定められており、各データ同士の関係性が密となっていることから、SQLを使用するDBの採用を予定している。
- 加えて、AZ障害時のフェイルオーバーを意識したMulti-AZ構成の有効化を実践することも目的の一つである。
- そのため、自動でMulti-AZ構成が適用され、リレーション構造を持たず柔軟にデータを格納出来るNoSQLが採用されているDynamoDBは適さない。
- また、Auroraに関してはSQLが採用されているが、RDSと比較して高性能であり、今回のような小規模のサービスではオーバースペックのため<br>
採用を見送った。ただ、今後サービスの規模拡大とともにデータ量が増加した場合はAuroraの使用も検討している。<br>

以上のことから、データの構造が明確かつデータ同士の関係性が密なSQLが採用されており、<br>
Multi-AZ構成の使用時には設定の有効化が必要となるRDSを採用した。

### VPC外リソース
| 名称 | サービス内容 | 特徴 |
|:-----:|:-----:|:-----:|
| Route 53 | 名前解決 | ドメイン名からIP変換を行う <br> DNSヘルスチェックで正常なエンドポイントにIP変換 |
| CloudWatch | メトリクス監視 | 各リソースのメトリクスを監視 <br> 閾値を超えた際はAlarmからSNSへ異常通知 |
| SNS | イベント通知 | CloudWatch Alarm からの異常通知を通知先へ連絡 |
- 今回は単一リージョンの作成になるが、今後規模拡大を想定した際にはリージョン障害時にも
サービスを継続するための可用性を確保する必要がある。
- また、トラフィックやリソースが異常値を記録した際には管理者に通知し、トラブルの対応とともに
原因解明と障害の解析が必要となる。<br>

そのため、今回はフェイルオーバールーティングが可能なRoute 53、
各リソースのメトリクス監視および異常検知のためのCloudWatch Alarm、
サービスからの通知を受け取り、事前に指定した宛先に通知するSNSを採用した。<br>
<br>
なお、今後はCloudTrailで各ユーザーのAPI操作履歴の確認、AthenaでS3やCloudTrailのログをクエリして
詳細な原因特定を実行可能とする予定である。

### 補足：Webサーバー
| サーバー名 | 特徴 |
|:-----:|:-----:|
| Nginx | 軽量、リバースプロキシが得意 | 
| Apache HTTP Server | 実績豊富、既存システムで多用 | 
| Internet Information Services | Windows専用 | 

- 今回のEC2で使用するAPIは Amazon Linux 2023 のため、Windows専用のWebサーバーであるInternet Information Servicesは除外した。

- また、EC2のインスタンスタイプが「t4g.micro」と小規模であり、API構築としてFastAPI(Python)の使用を予定していることから、軽量かつリバースプロキシとしてリクエストの振り分けが可能なNginxを採用した。

### 補足：インスタンスタイプ(EC2,RDS)
| サービス名 | 使用インスタンス |
|:-----:|:-----:|
| EC2 | t4g.micro | 
| RDS | t4g.micro | 

- コスト面を考慮し、高負荷時にバースト可能なTシリーズを採用。一般的に多用されるMシリーズも検討したが、本成果物は個人構築のアプリケーションであり、低コストでの構築を希望したためMシリーズの採用を見送った。

- 上述の通り個人構築のアプリケーションのため、large等のリソースサイズでは開発規模に対してオーバースペックとなり余分なコストが発生する。そこで開発規模に見合ったmicroを選定した。
